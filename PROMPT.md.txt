4. LOCAL FILE STORAGE AND STREAMING

Store files using a server-controlled layout such as:

_storage/yyyy/MM/dd/{objectId}/content.bin

The object-specific directory must prevent collisions between files uploaded on the same day.

Make the storage root configurable and keep it outside the public web root.

Implement genuine streaming uploads:

* Parse multipart uploads using a streaming approach such as MultipartReader.
* Do not rely on IFormFile model binding that buffers uploads.
* Do not read the whole file into a byte array, MemoryStream, string, or Base64 representation.
* Bounded reusable buffers are acceptable.
* Compute SHA-256 incrementally while writing.
* Count the actual bytes read.
* Enforce the configured file-size limit even when Content-Length is absent or inaccurate.
* Bound multipart headers, field sizes, section counts, filenames, and tag input.
* Define behavior for missing file parts, multiple file parts, and empty files.
* Clean up partial files after errors or cancellation.

Support a real upload of at least 100 MB with the default demonstration configuration. State whether the configured units are decimal MB or binary MiB.

Align file-size limits with API server and reverse-proxy request limits, allowing for multipart overhead.

Implement atomic writes:

* Write to a unique temporary file.
* Place temporary and final files on the same filesystem.
* Close the completed stream before moving it to the final path.
* Commit the content with an atomic rename or equivalent supported operation.
* Never expose a partially uploaded file.

SQL Server and the filesystem do not share a transaction. Explicitly handle:

* File write failure.
* Database persistence failure.
* Request cancellation.
* Filesystem rename failure.
* Process crashes between filesystem and database operations.

Use practical compensation and a documented recovery or reconciliation strategy. Clearly distinguish failures handled immediately from crash windows handled later.

Do not claim a database transaction makes filesystem operations transactional.

5. FILESYSTEM SECURITY

Never construct filesystem paths from user-provided filenames or route values.

Use opaque, server-generated keys. Resolve paths under the configured storage root and verify containment correctly.

Sanitize the original filename for display and response headers:

* Remove path components.
* Reject or remove control characters.
* Prevent response-header injection.
* Apply a reasonable length limit.

Account for both slash and backslash traversal attempts.

Document that storage directories are application-controlled and must not be writable by untrusted users. Avoid following unexpected symbolic links or reparse points where relevant.

Do not trust a client-supplied content type as proof of file contents.

Define a configurable upload policy for:

* Maximum size.
* Allowed extensions and/or content types.
* Filename length.
* Tag count and tag length.

For inline previews, use a conservative allowlist and suitable content validation. Do not serve HTML or SVG inline as trusted application content.

Keep arbitrary downloads as attachments and set appropriate security headers, including X-Content-Type-Options.

Do not expose physical storage paths, secrets, or stack traces to clients.
